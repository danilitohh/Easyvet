# Easyvet — revisión estática del aislamiento multi-tenant

**Fecha:** 2026-10-16  
**Alcance:** código NestJS/Prisma, esquema, pruebas de integración presentes y configuración del job de CI.  
**Método:** revisión estática y lectura de pruebas; no se enviaron cargas de explotación ni se modificó la base de datos.

## Límites importantes de la evidencia

- El job `.github/workflows/ci.yml` crea ahora `veterinary` como `LOGIN NOSUPERUSER NOBYPASSRLS`, verifica esos atributos y comprueba el bloqueo de `anon` y `authenticated` después de aplicar las migraciones. Esto mejora la representatividad de las pruebas de integración, pero **no** prueba todavía el rol efectivo de Production.
- La auditoría de catálogo de Supabase registrada en `docs/migration/SECURITY_AUDIT.md` observó RLS deshabilitado en las tablas de negocio antes de la migración `20261016220000_enable_defense_in_depth_rls`, y sin privilegios directos de tablas/esquema para `anon` y `authenticated`; `api_rate_limit_buckets` era la excepción con RLS forzado. La API sigue siendo la frontera de acceso observada para los datos de negocio.
- La vista protegida `GET /api/v1/platform/database-posture`, consultada en Production con la sesión del super admin, confirmó que Prisma usa el rol `postgres`: `bypassesRowLevelSecurity: true` y `superuser: false`. Por tanto, el runtime actual puede omitir RLS aunque no sea superusuario; esta evidencia no debe confundirse con el rol del editor SQL.
- La migración de defensa en profundidad fuerza RLS en las tablas públicas de aplicación y conserva la prueba con `veterinary` sin `BYPASSRLS` en la base efímera de CI. No elimina todavía el bypass del runtime productivo `postgres`; hacerlo requiere un contexto de organización por transacción y pruebas con dos tenants.
- No se ejecutó Strix ni una prueba de penetración: la herramienta usa payloads que pueden cambiar datos y requiere autorización específica. Este informe no es una certificación de seguridad.

## Resultado y siguiente control

En la revisión estática no se confirmó un bypass cross-tenant en las rutas y patrones examinados. Los filtros server-side y varias restricciones relacionales ofrecen controles útiles. La migración añade RLS como defensa de profundidad para evitar exposición directa futura de las tablas, pero el runtime de Production usa `postgres` con capacidad de omitir RLS; por tanto, el aislamiento de base de datos no se considera cerrado hasta eliminar ese bypass o justificarlo con una arquitectura de contexto por transacción verificable.

El siguiente paso seguro es mapear cómo la API debe establecer el contexto de organización por transacción para que el runtime productivo pueda dejar de usar `BYPASSRLS`, y probarlo con datos de dos organizaciones. No se debe cambiar el `DATABASE_URL` de Production ni eliminar el bypass hasta validar esos predicados y todas las rutas tenant-aware.
