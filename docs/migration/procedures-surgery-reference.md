## VERIFIED LEGACY BEHAVIOR

### Procedure y Surgery

No hay tabla relacional propia de Surgery/Procedure: el evento vive en `clinical_consultations` con `consultation_type = "Cirugia / procedimiento"` (variantes de tildes/espacios). Comparte record, paciente, tutor, CRUD y validación con consultas. La UI agrupa cirugía y procedimiento y no ofrece dos workflows/entidades distintos. No hay evidencia para dos agregados raíz.

Columnas exactas de `clinical_consultations`: `id`, `record_id`, `patient_id`, `owner_id`, `consultation_at`, `consultation_type`, `title`, `summary`, `indications`, `attachments_summary`, `document_reference`, `referred_to`, `consent_required`, `consent_id`, `professional_name`, `professional_license`, `created_at`, `updated_at`. Relaciones, fecha, tipo, título, resumen, profesional y licencia son NOT NULL en SQL; `consent_required` default false. No se observó FK SQL de `consent_id` en DDL.

`validate_consultation` requiere record, tipo, título, resumen, nombre profesional y licencia. Fecha, indicaciones, adjuntos, referencia documental, referido y consentimiento son opcionales; persistencia completa fecha ausente con hora actual. Formulario de Procedure sí pide fecha y nombre; el nombre se usa también como título.

Estados `Programada`, `En curso`, `Realizada`, `Cancelada` son texto dentro de `document_reference.perioperativeProtocol`, no lifecycle de consulta ni transiciones server-side. La UI cae a `Realizada` si hay `endTime`, o `Registrada` de lo contrario. No hay estados DRAFT/FINALIZED/VOIDED.

`document_reference` tiene JSON flexible: `kind: "procedure"`, `name`, `description`, `perioperativeProtocol`, `complications`. Parte se copia también a `summary`, `indications`, `attachments_summary` o payload (`treatment`, `observations`, `complications`). Se aceptan aliases/fallbacks y datos duplicados, por lo que el mapeo requiere parseo defensivo.

Campos del protocolo: `consentSigned`; `anestheticRisk`; `fastingStatus`; `surgicalResponsible`; `anesthesiaResponsible`; `auxiliary`; `area`; `side`; `status`; `startTime`; `endTime`; `monitoring`; `findings`; `bleeding`; `closure`; `observations`; `recoveryStatus`; `ownerCommunication`; `dischargeRecommendations`; `nextControlAt`; listas `preoperative`, `intraoperative`, `postoperative`. Cada medicamento usa `{ medication, dose, route, frequency, notes }`, todo texto libre; no crea movimiento de inventario.

### Anesthesia y monitorización

Anestesia se almacena como otra fila de `clinical_consultations` (`consultation_type: "Registro anestesico"`, también con acentos) y JSON `document_reference.kind: "anesthesia"`. UI permite “Sin cirugía vinculada” o `procedureId`; lista varios registros por cirugía.

Payload: `kind`, `procedureId`, `procedureName`, `startedAt`, `endedAt`, `anesthesiologist`, `anesthesiologistLicense`, `asa`, `technique`, `preanestheticEvaluation`, `medications` (texto libre), `airway`, `fluids`, `monitoring`, `complications`, `recovery`, `observations`, `intervalMinutes` (el formulario usa 10). El servidor genérico no valida esquema anestésico profundo.

Cada item `monitoring`: `time`, `heartRate`, `respiratoryRate`, `temperature`, `spo2`, `etco2`, `bloodPressure`, `plane`, `observations`. UI agrega filas de 10 min, requiere hora para al menos una, evita `endedAt < startedAt`; los signos son strings que pueden estar vacíos. El `monitoring` perioperatorio de cirugía es otro campo, no esa serie temporal.

El PDF de registro anestésico genera formulario en blanco desde paciente/tutor/configuración, no necesariamente un registro persistido. El reporte quirúrgico busca la consulta más reciente del paciente en tipos de cirugía/procedimiento. No son exports inmutables anclados a ID/versionado del evento.

### Equipo, tutor, snapshots, consentimiento y documentos

El protocolo conserva `surgicalResponsible`, `anesthesiaResponsible`, `auxiliary` como texto; anestesia repite nombre y licencia del anestesiólogo. No se verificó relación a Membership. Consulta requiere `professional_name` y `professional_license`, ambos strings. Legacy no garantiza snapshots históricos uniformes de Patient/Owner; los registros referencian ambos IDs y pantallas/exports pueden resolver los datos actuales.

`consents` es tabla independiente con `id`, `patient_id`, `owner_id`, `consent_type`, `procedure_name`, `risks_explained`, `benefits_expected`, `alternatives`, `cost_estimate`, `owner_statement`, `owner_signature_name`, `owner_identification`, `professional_name`, `professional_license`, `signed_at`, `notes`, `record_id`, `consultation_id`, `created_at`. Validación exige paciente/tipo/procedimiento/riesgos/manifestación/nombre e identificación del firmante/profesional/licencia/fecha; los demás campos son opcionales.

La consulta conserva `consent_required` y `consent_id`; persistencia valida que Consent pertenezca al mismo Patient. El JSON `consentSigned` es un booleano independiente, no prueba identidad ni firma real. Consentimiento PDF y solicitudes de firma son flujos separados; solicitud puede vincularse a consulta, sin garantía de que toda Surgery/Anesthesia esté firmada.

`attachments_summary`/`document_reference` guardan referencias/metadata; consulta soporta assets y export PDF/DOCX. No se considera que un texto legacy sea un archivo durable importable sin política de documentos.

### Agenda, Kardex, operaciones y permisos

Agenda usa `appointments`; `source_consultation_id` aparece en controles/seguimientos de consulta. El `status=Programada` del protocolo no reserva un slot ni equivale a Appointment; no se verificó una relación canónica de cirugía con Agenda. Kardex/hospitalización es módulo distinto; listas de medicamentos perioperatorios no son evidencia de administración/consumo.

Rutas observadas: `POST /api/consultations`, `GET /api/consultations/:id`, `GET /api/consultations/:id/assets/:index`, `DELETE /api/consultations/:id`; PDFs específicos reciben Patient ID. Save hace insert/upsert de consulta sin lifecycle clínico. Delete hace hard-delete y limpia dependencias ligadas conforme al servicio; no hay Void ni protección especial al estar “realizada”.

El catálogo de permisos separa `surgeries` (view/create/edit/delete) de `consents:general` (view/create/edit); Surgery y registro anestésico se clasifican como `surgeries`. La autorización es central aunque las rutas sean delgadas. `test_action_permissions.py` cubre permisos por acción, autoridad server-side y rutas alternativas.
